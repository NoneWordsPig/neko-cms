# neko-cms

> **a robot on cms** —— 一个在「聪明山」（raricy.com）上陪人聊天的猫娘机器人。

站点侧给站外开发者留了两份接口契约：`docs/comment-bot.md`（评论区）与 `docs/chat-bot.md`（聊天区）。
本项目是那两份契约的一个实现：**没有专用机器人接口**，她就是一个普通的 core+ 账号，
走和人完全一样的 HTTP 接口。本文解释各功能的实现原理。

## 能做什么

| 能力 | 说明 |
| --- | --- |
| 评论区陪聊 | 轮询全站最近评论，有人提到她（`neko` / `妮可`）就回复 |
| 读原博客 | 被提到的评论挂在哪篇文章下，她就先把那篇文章读了再回话（长文先概括） |
| 读上下文 | 用整棵评论树还原“这条评论所在的那串对话”，而不是只看孤零零一句 |
| 聊天区搭话 | 轮询大区 `lobby` 的对话：被点名 / 被引用必回；没人叫她也可能按兴趣插一句 |
| 只回一次 | 同一句提及最多回复一次，重启、重连都不会补第二遍 |
| 不自己刷自己 | 自己发的内容即使写了自己的名字也不触发；必须人类先开口 |

## 快速开始

```bash
pip install requests openai python-dotenv
cp .env.example .env          # 填入 API Key 与站点账号密码
python neko.py                # 正式运行
```

演习模式（只打印、不发送任何内容，状态写另一个文件）：

```bash
NEKO_DRY_RUN=1 python neko.py                          # 只盯着看
NEKO_DRY_RUN=1 NEKO_REPLAY_BACKLOG=1 python neko.py    # 把最近 100 条评论 / 最近一页聊天也过一遍
```

Windows 自启动：`neko_launcher.py`（在上一级目录）是守护进程，崩了等 30 秒重来；
把它挂到 `HKCU\Software\Microsoft\Windows\CurrentVersion\Run` 就能开机登录后自动拉起。

## 环境变量

| 变量 | 默认 | 说明 |
| --- | --- | --- |
| `API_KEY`（或 `api_key`） | 无 | DeepSeek API Key，**必填** |
| `NEKO_USERNAME` | `neko` | 机器人账号（站点要求 core+ 角色） |
| `NEKO_PASSWORD` | 无 | 账号密码，**必填，只写在 .env 里**（源码刻意不留默认值） |
| `RARICY_BASE_URL` | `http://raricy.com:5000` | 站点地址 |
| `NEKO_BOT_USERNAMES` | `neko,NebulaFera,Logos` | 非人类账号：它们发的内容不触发回复 |
| `NEKO_DRY_RUN` | 关 | `1` = 演习模式，不发送 |
| `NEKO_REPLAY_BACKLOG` | 关 | 补看历史，**仅在 `NEKO_DRY_RUN=1` 时生效** |

可调参数集中在 `neko.py` 顶部常量区：

| 常量 | 默认 | 含义 |
| --- | --- | --- |
| `POLL_INTERVAL` | 5 秒 | 主循环节奏（聊天区按它轮询） |
| `COMMENT_POLL_INTERVAL` | 30 秒 | 评论轮询周期 |
| `COMMENT_MAX_PER_HOUR` / `CHAT_MAX_PER_HOUR` | 30 / 15 | 两条通道各自的小时回复上限（安全阀） |
| `CHAT_MIN_INTERVAL` | 60 秒 | 相邻两次“按兴趣搭话”的最小间隔（点名不受限） |
| `CHAT_AMBIENT_PROBABILITY` / `CHAT_AMBIENT_INTENTION` | 25 / 40 | 没人叫她时“看到并想搭话”的基础概率与意愿 |

## 整体结构

单进程、同步轮询，没有队列也没有数据库：

```
main()                      死循环，每 POLL_INTERVAL 一轮
├── poll_comments()         每 COMMENT_POLL_INTERVAL 跑一次
│   ├── fetch_recent_comments()   GET /api/spider/comments（最近 100 条）
│   ├── select_new_comments()     按“锚点 id 的位置”挑出新评论
│   └── handle_comment()          判定 → 掷骰 → 取上下文 → 生成 → 认领 → 发送
└── poll_chat()
    ├── fetch_lobby_context()     GET .../lobby/messages?limit=30（聊天上下文）
    ├── fetch_lobby_new()         GET .../lobby/messages?after=<游标>（增量）
    ├── merge_timeline()          合成一条按 id 排序的时间线
    └── handle_chat_message()     判定 → 掷骰 → 生成 → 认领 → 发送

静默层：load_state / save_state（neko_state.json）—— 轮询游标、去重表、频控时刻
```

## 功能实现原理

### 1. 登录与会话

`POST /api/auth/login` 换取 HttpOnly Cookie（`raricy_session`，30 天）。三个处理点：

- **会话会过期、也会被主动作废**（改密码 / 被降权会让旧 Cookie 立刻失效）→
  `api_request()` 收到 401 就自动重登一次并重放这次请求；
- **不设 `Origin` / `Referer`**：站点对写请求校验同源，但两个头都缺失时放行，
  非浏览器客户端天然通过；自己伪造反而可能被判跨源而 403；
- **`session.trust_env = False`**：绕开系统代理 —— 本机代理挂掉时 `requests`
  会直接抛 `ProxyError` 把机器人打死（日志里真实发生过）。

### 2. 评论怎么“发现新的”

`GET /api/spider/comments` 只给最近 100 条，而且**评论 id 是 UUID，没有自增游标**
（这点和聊天消息不同）。所以增量只能这样算：

1. 记住上次见到的最新那条 id 当**锚点**；
2. 下次在新窗口里找锚点的位置，排在它前面的就是新评论；
3. 锚点已经掉出 100 条窗口 → 整窗都当新的（去重表兜底，不会重复回）；
4. 顺序反过来（旧 → 新）逐条处理，保证同一批里对话顺序自然。

### 3. 什么情况下她会开口

| 触发 | 看到概率 | 基础意愿 |
| --- | --- | --- |
| 评论里出现 `neko` / `妮可` | 100 | 100 |
| 在她自己发的博客下评论（顶层） | 100 | 50 |
| 回复她自己的评论 | 100 | 90 |
| 与她无关的评论 | 0 | 20（只读不回） |
| 聊天区点名 / 引用回复她 | 100 | 100 / 85 |
| 聊天区她刚说完、对方接着说话 | 100 | 70 |
| 聊天区普通闲聊（没人叫她） | 25 | 40 |

“概率”是**有没有看见**，“意愿”是**想不想回**，两次都用 `random.randint(1, 100)`
和阈值比大小 —— 数值与老版本逐字一致，聊天那几行是新加的。

### 4. 读“被 @ 的那条评论所在的原博客”

`GET /api/spider/blogs/:id` → `{meta: {title, author, ...}, content}`：

- 正文 ≤ 4000 字：整篇进上下文；
- 超过：先让她自己写一份 300 字小结（最多喂 2 万字进去），概括失败就降级成“只读开头”。

### 5. 对话上下文：为什么用评论树

`GET /api/blogs/:id/comments` 一次返回整棵评论树，每条都带 **Markdown 原文 `content`**；
用 DFS 找出目标评论的祖先链，拼成 `用户名: 内容` 的对话记录（截到 3000 字）。

不用“逐级回查父评论”的原因：spider 单条接口只给转义后的 `content_html`
（HTML 转义 + `<br>`，不是 Markdown），而且父评论一旦被删，链就断了。
树一次给全，还能顺带判断“这条评论是不是已被隐藏”（找不到就干脆不回）。

### 6. 聊天区怎么读、怎么接

读两条流合成一条时间线：

- `?limit=30` 拿最近一页 → 当**上下文**；
- `?after=<游标>` 拿新消息 → 当**待处理**（消息 id 全局自增，可当游标；必要时翻页，最多 5 页）。

两份按 id 去重合并，取目标消息**之前**最近 30 条当“聊天记录”喂给模型。
只有“直接跟我说话”（点名 / 引用）才用 `@用户名 ` 开头并带 `reply_to` 引用原消息；
没人叫她时搭话不 @ 任何人 —— @ 会给对方发通知，闲聊不该打扰人。

### 7. “想不想回”是问模型要一个数

`deepseek-chat` + `response_format=json_object` → `{"intention": 0~100}`，再和随机数比较。
提示词 = 人格设定（`self_introduction`）+ 场景说明 + JSON 输出示例（两处场景：
评论区 / 聊天区，聊天那版会额外带上最近的聊天记录）。

## 安全设计

### 至多一次：先认领，再发送

`claim_trigger()` 把这条触发的 id 记进 `handled_*` 并**立刻原子落盘**
（写临时文件 + `os.replace`），然后才发请求。于是：

- 轮询窗口反复看到同一句 → 去重表挡住；
- 进程重启 → 状态文件还在，不会补发；
- 崩在发送途中 → 最坏漏回一条，**绝不重复回**。

顺序是刻意如此的：宁可漏，不重复。反过来“先发后记”，崩溃时就会重复回。

### 自己的内容不触发

`is_bot()` 用 `BOT_USERNAMES`（默认 `neko,NebulaFera,Logos`）过滤：自己发的评论 / 消息
即使正文里出现自己的名字也不回；其它机器人同理 —— 机器人互相喊名字不会滚成无限循环。

### 必须人类先开口

判定表里所有“会回”的分支都要求发言者是**人类**：提到我 / 回复我的评论 /
引用我的消息 / 接着我的话头。她不会凭空自己往下说。

### 一个真实修过的 bug

最早“两条聊天消息至少隔 60 秒”的冷却不分场合，结果**点名落在冷却窗口里会被静音吃掉**
（线上真实发生：有人叫 `neko`、有人 `@neko`，两句都没回）。现在 `chat_trigger()`
额外返回一个 `addressed`（这句话是不是冲我说的）：点名 / 引用 / 接话不受冷却限制，
只有“没人叫、按兴趣搭话”才吃冷却。

### 节流与保险丝

| 机制 | 默认 | 为什么 |
| --- | --- | --- |
| 评论小时上限 | 30 | 站点硬上限是 2000 条 / 天，但“见评论就回”会骚扰人、也可能被禁言 |
| 聊天小时上限 | 15 | 聊天是 30 次 / 分 + 2000 条 / 天的硬上限，失控会烧光额度 |
| 聊天最小间隔 | 60 秒 | 只管“按兴趣搭话”，防刷屏 |
| 评论发送后冷却 | 15 秒 | 一条一条来，别让人看见刷屏 |
| 长度保险丝 | 评论 2000 / 聊天 800 字 | 站点上限是 5000 字，她自己用不上那么长 |
| 去重表裁剪 | 保留 1000 条 | 状态文件不无限长大 |

## 踩过的坑

| 现象 | 原因与处理 |
| --- | --- |
| 登录直接抛 `JSONDecodeError` | 老接口 `/auth/login`、`/blog/spider/*` 在站点迁到 Next 后已 404，全部改走 `/api/*` |
| `ProxyError 127.0.0.1:7897` | 本机代理挂掉时 `requests` 仍会走环境代理 → `session.trust_env = False` |
| 打印带 emoji 的日志直接崩 | Windows 控制台是 GBK，博客标题里的 🐾 触发 `UnicodeEncodeError` → 启动时 `reconfigure(errors='replace')` |
| 自启动后看不到任何输出 | 自启动用 `pythonw.exe`（没有控制台），`print` 被丢弃；只有 launcher 的崩溃日志 |
| 时间戳凭空多 8 小时 | 站点时间戳是“UTC+8 墙上时间贴 Z 标签”；本项目不解析时间，故无影响 |

## 状态文件

`neko_state.json`（演习模式写 `neko_state.dryrun.json`，两者都不入库）：

| 字段 | 含义 |
| --- | --- |
| `last_comment_id` | 评论轮询锚点（UUID，只能记“最新那条”） |
| `last_chat_id` | 聊天区轮询游标（消息 id 自增） |
| `handled_comments` / `handled_chat` | 已回复过的触发 id（去重表，最多留 1000 条） |
| `comment_reply_times` / `chat_reply_times` | 回复时刻，用于小时限额 |
| `last_chat_reply_at` | 上次在聊天区说话的时刻，用于最小间隔 |

删掉它 = 让她忘掉一切；但**首次运行不会回补历史**（避免上线瞬间刷屏）。
想先看历史会怎么回，用 `NEKO_DRY_RUN=1 NEKO_REPLAY_BACKLOG=1`。

## 已知限制

- 只管大区 `lobby`，不处理私聊（接口支持，未实现）；
- 用轮询而不是 SSE：评论本来就没有推送；聊天有 SSE，但轮询更简单、够用；
- 图片消息、拍一拍、纯表情不回复（没有可判的文本）；
- **别同时跑两个实例**：认领不是跨进程互斥的，两个进程会各认各的、可能重复回复；
- 长文摘要会丢细节 —— 她“读”到的只是摘要加上你自己那句话。
