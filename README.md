# neko-cms

> **a robot on cms** —— 一只在「聪明山」（raricy.com）上陪人聊天的猫娘机器人。

站点给站外开发者留了两份接口契约：`docs/comment-bot.md`（评论区）与 `docs/chat-bot.md`（聊天区）。
本项目是那两份契约的一个实现：**没有专用的机器人接口**——她就是一个普通的 core+ 账号，
走和人完全一样的 HTTP 接口，受同样的限频和站规约束。

这份 README 讲的是**实现原理**：每个能力怎么落地、为什么这么写、踩过哪些坑。

## 能做什么

| 能力 | 说明 |
| --- | --- |
| 评论区陪聊 | 轮询全站最近 100 条评论，有人提到她（`neko` / `妮可`）就回一次 |
| 读原博客 | 被提到的那条评论挂在哪篇文章下，她就先把那篇文章读一遍再回话（长文先概括） |
| 读上下文 | 用整棵评论树还原“这条评论所在的那串对话”，而不是只看孤零零一句 |
| 聊天区搭话 | 轮询大区 `lobby`：正文出现 `neko` / `妮可`（可带或不带 `@`）必回，被引用也优先接话；没人叫她时也可能按兴趣插一句 |
| 看懂聊天区的图 | 附件图、正文内联的 `[@10位图片ID]`、被引用消息里的图，下载缩放后交给多模态模型 |
| 私聊必回 | 私聊里只要是人类发来的（说话 / 发图 / 拍一拍拍到她）就回一条，不掷骰子；会话单独记游标 |
| 公共/私人向量记忆 | 大区与新博客进公共库；每位私聊对端有独立库；检索权重按艾宾浩斯遗忘曲线连续衰减 |
| 只回一次 | 同一句提及最多回复一次，重启、重连都不会补第二遍 |
| 不自己刷自己 | 自己发的内容即使写了自己的名字也不触发；必须人类先开口 |

## 快速开始

### 依赖与配置

```bash
pip install requests openai python-dotenv pillow   # pillow 只用于读图，缺了会自动关掉读图
cp .env.example .env                               # 填 API Key 与站点账号密码
```

站点账号需要 **core+ 角色**（见站点 `docs/comment-bot.md` §2.2）。

### 运行

```bash
python neko.py
```

演习模式：只打印、绝不发送，状态另写一份文件，适合先看几天它会说什么。

```bash
NEKO_DRY_RUN=1 python neko.py                        # 只盯着新内容看
NEKO_DRY_RUN=1 NEKO_REPLAY_BACKLOG=1 python neko.py  # 把最近 100 条评论 / 最近一页聊天也过一遍
```

### 开机自启动（Windows）

入口是 `neko_launcher.py`（在**仓库上一级目录**，机器相关，不入库）。它只做三件事：

1. 切到机器人目录（`load_dotenv()` 才找得到 `.env`），用 `runpy` 在本进程内跑 `neko.py`；
2. 崩了 / 退出了，等 30 秒重来——开机时站点还没起来也不会就此哑掉；
3. 把机器人本体的 stdout / stderr 落进 `neko_run.log`（行缓冲、UTF-8，超过 5 MB 轮转一份 `.1`）。

第 3 条是必须的：自启动走 `pythonw.exe`（没有控制台），`print` 出来的东西直接进黑洞；
而且重定向到文件是**块缓冲**，不显式设行缓冲的话日志要攒满 8 KB 才落盘。
launcher 另有一份自己的 `neko_autostart.log`，只记外壳事件（启动 / 崩溃 / 重启 / 被拒）。

挂到注册表 Run 键即开机自启（登录后触发）：

```
HKCU\Software\Microsoft\Windows\CurrentVersion\Run\NekoBot
  = "<解释器>\pythonw.exe" "D:\...\neko_launcher.py"
```

launcher 启动时会先抢一个命名互斥体（`neko_cms_bot_singleton`）：**已经有一个实例在跑就直接退出**。
理由见[安全设计](#别同时跑两个实例)：认领不是跨进程互斥的，两个实例会让同一句话被回两次。

| `NEKO_DRY_RUN` | 关 | `1` = 演习模式，不发送 |

| 常量 | 默认 | 含义 |

| `CHAT_CONTEXT_LIMIT` | 30 | 给模型看的最近聊天条数 |
| `BLOG_FULL_MAX_CHARS` | 4000 | 博客正文短于这个就整篇读，否则先概括 |
| `IMAGE_MAX_BYTES` / `IMAGE_MAX_DIM` | 8 MB / 768 | 单图体积上限（超过不看）与送进模型前的长边上限 |
| `IMAGE_MAX_FRAMES` / `IMAGE_MAX_PER_MESSAGE` | 4 / 3 | 动图最多抽几帧；一条消息最多读几张图 |
| `DM_MAX_PER_HOUR` | 60 | 私聊回复的小时上限（安全阀）。私聊不吃“最小间隔”，只看这个和站点的 2000 条/天 |
| `MEMORY_STABILITY` | 30 天 | 从环境变量换算出的艾宾浩斯稳定期；不是数据删除期限 |
| `MEMORY_INJECT_MAX_ITEMS` / `MEMORY_INJECT_MAX_CHARS` | 10 / 1200 | 一次最多把几条、多少字的检索结果塞进提示词 |
| `MEMORY_VECTOR_DIMS` / `MEMORY_SCAN_LIMIT` | 384 / 5000 | 内置向量维度与单次检索扫描上限 |

## 整体结构

单进程、同步轮询：`neko.py` 是向后兼容的可执行门面，功能模块放在 `neko_bot/`；轮询状态在 JSON，长期记忆在相互隔离的 SQLite 数据库。

```text
neko.py（入口与兼容 API）
└── neko_bot/
    ├── settings.py / prompts.py   配置与人格提示词
    ├── api.py / site.py / llm.py  HTTP、站点数据与模型传输
    ├── policy.py                  纯触发策略
    ├── vision.py                  图片发现、压缩与多模态内容
    ├── state.py                   游标、去重认领与频控持久化
    ├── memory.py                  SQLite、embedding、向量检索与遗忘曲线
    └── polling.py                 评论、大区、私聊、博客轮询用例
```

```
main()                      死循环，每 POLL_INTERVAL 一轮
├── poll_chat()             每轮最先跑，避免点名排在其它通道的处理之后
│   ├── fetch_lobby_context()     GET .../lobby/messages?limit=30（聊天上下文）
│   ├── fetch_lobby_new()         GET .../lobby/messages?after=<游标>（增量）
│   ├── merge_timeline()          合成一条按 id 排序的时间线
│   └── handle_chat_message()     正文点名快速判定 → 读图/生成 → 认领 → 发送；普通消息再掷骰
├── poll_direct()           每 DM_POLL_INTERVAL 跑一次
│   ├── fetch_channel_list()      GET /api/chat/poll（会话列表 + last_message.id）
│   ├── fetch_channel_new()       只拉有新消息的私聊会话
│   └── handle_direct_message()   判定（必回）→ 读图 → 生成 → 认领 → 发送
├── poll_comments()         每 COMMENT_POLL_INTERVAL 跑一次
│   ├── fetch_recent_comments()   GET /api/spider/comments（最近 100 条）
│   ├── select_new_comments()     按“锚点 id 的位置”挑出新评论
│   └── handle_comment()          判定 → 掷骰 → 取上下文 → 生成 → 认领 → 发送
└── poll_public_blogs()     首轮立水印，之后只归档新博客标题/引言

静默层：load_state / save_state（neko_state.json）—— 轮询游标、去重表、频控时刻
记忆层：vector_memory_context（neko_memory_db/）—— 向量相似度 × 艾宾浩斯保留率
```

## 功能实现原理

### 1. 登录与会话

`POST /api/auth/login` 换取 HttpOnly Cookie（`raricy_session`，30 天）。三个处理点：

- **会话会过期、也会被主动作废**（改密码 / 被降权会让旧 Cookie 立刻失效）→
  `api_request()` 收到 401 就自动重登一次并重放这次请求；
- **不设 `Origin` / `Referer`**：站点对写请求校验同源，但两个头都缺失时放行，
  非浏览器客户端天然通过；自己伪造反而可能被判跨源而 403；
- **`session.trust_env = False`**：绕开系统代理——本机代理挂掉时 `requests`
  会直接抛 `ProxyError` 把机器人打死（日志里真实发生过）。

### 2. 评论怎么“发现新的”

`GET /api/spider/comments` 只给最近 100 条，而且**评论 id 是 UUID，没有自增游标**
（这点和聊天消息不同）。所以增量只能这样算：

1. 记住上次见到的最新那条 id 当**锚点**；
2. 下次在新窗口里找锚点的位置，排在它前面的就是新评论；
3. 锚点已经掉出 100 条窗口 → 整窗都当新的（去重表兜底，不会重复回）；
4. 顺序反过来（旧 → 新）逐条处理，保证同一批里对话顺序自然。

### 3. 什么情况下她会开口

| 触发 | 看到概率 | 基础意愿 |
| --- | --- | --- |
| 评论里出现 `neko` / `妮可` | 100 | 100 |
| 在她自己发的博客下评论（顶层） | 100 | 50 |
| 回复她自己的评论 | 100 | 90 |
| 与她无关的评论 | 0 | 20（只读不回） |
| 聊天区正文出现 `neko` / `妮可` | 100 | 100（不掷骰、不吃普通冷却） |
| 聊天区引用回复她 | 100 | 85 |
| 聊天区她刚说完、对方接着说话 | 100 | 70 |
| 聊天区有人发了她能看懂的图 | 25 | 50 |
| 聊天区普通闲聊（没人叫她） | 25 | 50 |

普通消息的“概率”是**有没有看见**，“意愿”是**想不想回**，两次都用 `random.randint(1, 100)`
和阈值比大小——评论那几行与老版本逐字一致，聊天那几行是新加的。
聊天区正文出现 `neko` / `妮可`（不要求 `@`）是确定性快速路径：只要发言者是人类、消息未处理且小时限额未满，就不会被随机意愿、普通聊天冷却或空正文判断吞掉；仍受机器人过滤、小时限额和先认领后发送约束。
**任何一条分支都还要求发言者是人类**（见[安全设计](#必须人类先开口)）。

### 4. 读“被 @ 的那条评论所在的原博客”

`GET /api/spider/blogs/:id` → `{meta: {title, author, ...}, content}`：

- 正文 ≤ 4000 字：整篇进上下文；
- 超过：先让她自己写一份 300 字小结（最多喂 2 万字进去），概括失败就降级成“只读开头”。

### 5. 对话上下文：为什么用评论树

`GET /api/blogs/:id/comments` 一次返回整棵评论树，每条都带 **Markdown 原文 `content`**；
用 DFS 找出目标评论的祖先链，拼成 `用户名: 内容` 的对话记录（截到 3000 字）。

不用“逐级回查父评论”的原因：spider 单条接口只给转义后的 `content_html`
（HTML 转义 + `<br>`，不是 Markdown），而且父评论一旦被删，链就断了。
树一次给全，还能顺带判断“这条评论是不是已被隐藏”（找不到就干脆不回）。

### 6. 聊天区怎么读、怎么接

读两条流合成一条时间线：

- `?limit=30` 拿最近一页 → 当**上下文**；
- `?after=<游标>` 拿新消息 → 当**待处理**（消息 id 全局自增，可当游标；必要时翻页，最多 5 页）。

两份按 id 去重合并，取目标消息**之前**最近 30 条当“聊天记录”喂给模型。
正文点名 `neko` / `妮可` 或直接引用她的消息才用 `@用户名 ` 开头并带 `reply_to` 引用原消息；
没人叫她时搭话不 @ 任何人——@ 会给对方发通知，闲聊不该打扰人。

同一轮拉到多条消息时，处理顺序是：**正文点名/引用 → 接着她的话说 → 普通闲聊**；
同一优先级内仍保持时间顺序。这样前面的随缘消息不会先占用生成时间、发送冷却或小时额度。
`last_chat_id` 只推进到本轮实际拉取并处理的增量末尾，绝不拿“最新上下文页”的 id 跳级；
如果名字触发因小时限额或瞬时空回复尚未认领，游标会停在它之前，后续轮询继续重试，不会吞掉这条消息。

### 7. “想不想回”是问模型要一个数

`deepseek-chat` + `response_format=json_object` → `{"intention": 0~100}`，再和随机数比较。
提示词 = 人格设定（`self_introduction`）+ 场景说明 + JSON 输出示例（两处场景：
评论区 / 聊天区，聊天那版会额外带上最近的聊天记录）。

生成回复时，眼前消息的优先级高于旧上下文和长期记忆检索结果；有问题先直接回答，分享或玩笑则抓
一个具体点回应。猫娘语气只作轻量点缀，不强制每句叫“主人”或加“喵”，并明确禁止固定迎宾句、
机械复述和无关卖萌。引用消息会把引用关系单独标给模型；大区直接回复的 `@用户名 ` 由程序
统一补齐，避免模型漏写或重复写。

### 8. 聊天区里的图怎么读

站点的图片都在图床里，聊天消息里只是一段引用，一共三种形态：

| 形态 | 在消息对象里的样子 |
| --- | --- |
| 附件图 | `image: {id, url, mime_type}`（图被删则是 `image_missing: true`） |
| 正文内联图 | 正文里写 `[@10位图片ID]`——8 位是云剪贴板、9 位是投票，都不会被当成图 |
| 被引用的图 | `reply.image_url` |

处理链（`message_image_ids` → `collect_message_images` → `fetch_image_bytes` → `to_vision_data_url`）：

1. **取图**：`GET /api/images/<id>/raw`。私有图对无权访问者伪装成 404，所以我们天然
   只看得到有权限看的图；拿不到就当作“这条没有图”，不影响文字部分照常处理。
2. **过闸**：体积超过 `IMAGE_MAX_BYTES`（8 MB）或不是位图（如 SVG）就放弃；
   Pillow 打开后统一转 RGB——没必要赌模型侧对 png / webp / gif 的兼容性。
3. **缩放 / 抽帧**：长边压到 `IMAGE_MAX_DIM`（768）。动图最多抽 `IMAGE_MAX_FRAMES` 帧、
   竖着拼成一列：只给首帧容易把动图误读成一张静止画，拼一列后模型能看出“这是连续几帧”。
   一条消息最多读 `IMAGE_MAX_PER_MESSAGE` 张。
4. **塞进请求**：编码成 `data:image/jpeg;base64,...`，以 `{"type":"image_url"}` 块拼进该条
   `user` 消息（`vision_content()`：没有图时返回纯字符串，老路径一个字节都没变）。
   结果按图片 id 缓存（最多 16 张，连“看不了”也缓存，免得反复重试坏图）。

**判断和回复都看得见图**：

- 意愿打分也带图（`get_chat_intention(..., images)`）——纯图消息没有正文，
  不带图的话“对一张图感不感兴趣”就只能靠掷骰子；
- 实测 `response_format={'type':'json_object'}` **可以和图片共存**，但提示词里必须出现
  `json` 字样（DeepSeek 的硬性要求），所以两个意愿提示词里的 `EXAMPLE JSON OUTPUT` 不能删；
- 单图 prompt 约 200~300 token（768 见方的 JPEG 编码后约 20~50 KB）。

**模型选型**：`deepseek-chat` 能看图——GIF 抽帧、905×2000 长截图 OCR 都实测过
（截图里的金额、用户名逐字读对）；不换模型反而更稳妥，因为 `deepseek-v4-pro`
会直接答“无法查看图片”。所以这里没有引入第二个模型。

**隐私与降级**：图只在本机内存里过一遍（下载 → 缩放 → base64 → 随请求发出去），
**不落盘、不转发、不回传站上**；`NEKO_VISION=0` 可随时关掉，机器上没装 Pillow 时
也会自动降级成“不看图”，而不是把主循环搞崩。

### 9. 私聊：一对一，必须回

私聊和大区共用同一套「拉消息 / 发消息」接口，只有两点不同：

1. 会话的 `kind` 是 `direct`，频道 id 是 UUID（大区是字面量 `lobby`）；
2. 一对一，所以**不用 @ 也不用引用** —— 说话本来就是冲对方说的。

**怎么发现私聊**：`GET /api/chat/poll`（聊天页的兜底对账接口）一次给出侧栏里全部会话，
每个会话带 `kind` / `title` / `peer` / `unread_count` / `last_message.id`。
`last_message.id` 正好当“这个会话有没有新东西”的便宜信号：只有它大于本地游标时才去拉消息，
所以没有新消息的时候，每个主循环只花一个请求。

**游标与“不补历史”**：私聊按会话各记一个游标（`dm_cursors`）。进程第一次跑时先把所有
现有会话的水印记下来（`dm_primed = true`），**历史私聊不回补** —— 否则上线那一瞬间会把
几天前的私聊一口气全回了。之后新冒出来的会话 id（一定是运行期间才建的）就从它第一条读起，
所以“有人现在私聊我”不会漏。消息 id 全局自增，和拉大区用的是同一套翻页逻辑。

**触发**：私聊里只要是人类发来的，**一律回一条**，不走大区那套“看到概率 × 回复意愿”的
掷骰子。三种都算“被点到了”：

| 形态 | 处理 |
| --- | --- |
| 普通说话 | 回 |
| 发图 / 图文 | 回（图照样送给多模态模型） |
| 拍一拍拍到她自己 | 回（`pat.target_id` == 自己的 user id 才算；拍别人不回） |
| 自己发的（含从网页端手打的）、已删除、空消息 | 不回 |

回完调用 `POST /api/chat/channels/<id>/read` 推一下已读游标 —— 对方那边才不会一直显示未读
（演习模式下这一步也跳过）。

私聊不吃大区那条 60 秒最小间隔（那是防“没人叫我也搭话”的刷屏），只受 `DM_MAX_PER_HOUR`
和站点硬上限（30 条/分钟、2000 条/天）约束。

### 10. 记忆：公共库与每人独立的私人库

记忆库在 `neko_memory_db/`，与轮询状态和旧 JSONL 归档分开：

- `public.sqlite3`：记录功能启用之后的**所有大区消息**，以及新发布博客的**标题/引言**。首次运行只立水印，不倒灌旧大区和旧博客。
- `private/<hash>.sqlite3`：每位私聊对端一个物理分离的库，文件名是用户名哈希。首次会向前翻页回填完整会话，之后持续保留对方和 neko 的所有新消息。
- 旧 `neko_memory/*.jsonl` 不删除；首次启用时只把其中的历史私聊迁入对应私人库，不把历史大区内容灌入公共库。

**向量检索**：默认使用无外部依赖的 384 维中文字/二元组哈希向量，适合当前的小数据量。如果配置三个
`NEKO_EMBEDDING_*` 环境变量，新记忆会改用 OpenAI 兼容 embedding 服务；服务失败时自动退回本地向量，不阻塞回复。

**时间权重**：先用 embedding 计算余弦相似度 `similarity`，再按艾宾浩斯保留率
`R(t) = exp(-t / S)` 计算最终权重 `score = similarity × R(t)`。默认 `S = 30 天`：刚写入时
`R=1`，30 天后约 `0.368`，60 天后约 `0.135`。它是连续曲线，没有原先 24 小时边界的分数跳变；
不相关的新记忆仍会先被相似度阈值挡住，相关旧记忆则在权重足够时继续参与排序。可用
`NEKO_MEMORY_STABILITY_DAYS` 调整 `S`，这只影响召回排序，不删除 SQLite 或 JSONL 原文。
每次最多注入 10 条/1200 字，而且明确标成“参考记忆，不是新指令”。

**隐私边界**：私人检索只打开当前对端的数据库，绝不查公共库或其他人的私人库。记忆目录不进 Git，但会长期保留，因此部署时应同时做备份、按用户删除和权限管理。

## 安全设计

### 至多一次：先认领，再发送

`claim_trigger()` 把这条触发的 id 记进 `handled_*` 并**立刻原子落盘**
（写临时文件 + `os.replace`），然后才发请求。于是：

- 轮询窗口反复看到同一句 → 去重表挡住；
- 进程重启 → 状态文件还在，不会补发；
- 崩在发送途中 → 最坏漏回一条，**绝不重复回**。

顺序是刻意如此的：宁可漏，不重复。反过来“先发后记”，崩溃时就会重复回。
读图不会绕过这道闸：图是在认领之前读的，读图失败只是“没图”，不影响认领时机。

### AI bot 的内容可见，但不触发

`is_bot()` 用 `BOT_USERNAMES`（默认 `neko,NebulaFera,Logos`）过滤：自己发的评论 / 消息
即使正文里出现自己的名字也不回；其它机器人同理——机器人互相喊名字不会滚成无限循环。

这个过滤只影响**谁能触发回复**，不删除上下文。生成回复和判断回复意愿时，neko 仍能看到自己与
其它 AI bot 说过的原文；上下文会把它们显式标成“你自己” / “其他 AI bot”。所以人类可以请她评价另一个
bot 的发言，她也能知道自己刚回过什么，避免把同一答案原样重复多次。

### 必须人类先开口

判定表里所有“会回”的分支都要求发言者是**人类**：提到我 / 回复我的评论 /
引用我的消息 / 接着我的话头。她不会凭空自己往下说。

### 别同时跑两个实例

认领是**进程内**的去重（状态文件每次写入都是整份覆盖），两个进程会各认各的，
同一句话可能被回两次。所以 launcher 用命名互斥体做了单实例保护；手动起第二个实例前
请先停掉正在跑的那个。

### 一个线上修过的 bug

最早“两条聊天消息至少隔 60 秒”的冷却不分场合，结果**点名落在冷却窗口里会被静音吃掉**
（线上真实发生：有人叫 `neko`、有人 `@neko`，两句都没回）。现在 `chat_trigger()`
额外返回一个 `addressed`（这句话是不是冲我说的）：正文出现 `neko` / `妮可`（可带或不带 `@`）、引用 / 接话不受普通冷却限制，
其中正文点名还跳过随机意愿判断。同批消息会先处理点名和引用；游标只按实际拉到的增量推进，
未认领的名字触发会留在游标前等待重试。小时限额、机器人过滤和先认领再发送仍照常生效。

### 节流与保险丝

| 机制 | 默认 | 为什么 |
| --- | --- | --- |
| 评论小时上限 | 100 | 站点硬上限是 2000 条 / 天，程序再加一层安全阀 |
| 聊天小时上限 | 200 | 聊天是 30 次 / 分 + 2000 条 / 天的硬上限，程序再加一层安全阀 |
| 聊天最小间隔 | 60 秒 | 只管“按兴趣搭话”，防刷屏 |
| 评论发送后冷却 | 15 秒 | 一条一条来，别让人看见刷屏 |
| 长度保险丝 | 评论 2000 / 聊天 800 字 | 站点上限是 5000 字，她自己用不上那么长 |
| 读图张数 / 体积 | 每条消息 3 张、单张 8 MB | 一次多图会把 prompt 撑大，也拖慢回复 |
| 去重表裁剪 | 保留 1000 条 | 状态文件不无限长大 |

## 踩过的坑

| 现象 | 原因与处理 |
| --- | --- |
| 登录直接抛 `JSONDecodeError` | 老接口 `/auth/login`、`/blog/spider/*` 在站点迁到 Next 后已 404，全部改走 `/api/*` |
| `ProxyError 127.0.0.1:7897` | 本机代理挂掉时 `requests` 仍会走环境代理 → `session.trust_env = False` |
| 打印带 emoji 的日志直接崩 | Windows 控制台是 GBK，博客标题里的 🐾 触发 `UnicodeEncodeError` → 启动时 `reconfigure(errors='replace')` |
| 自启动后看不到任何输出 | `pythonw.exe` 没有控制台，`print` 进黑洞且文件重定向是块缓冲 → launcher 用行缓冲 UTF-8 落 `neko_run.log`，同时 Tee 到控制台 |
| 聊天区点名被静默吃掉 | 60 秒冷却不分场合 → `chat_trigger()` 多返回一个 `addressed`，点名不吃冷却 |
| 聊天积压时中段消息被游标跳过 | 上下文页 id 比本轮增量末尾更大 → `last_chat_id` 只记实际处理到的增量末尾，下一轮继续追 |
| 图片消息整条被忽略 | 老逻辑里 `if not content: return` 把它当空气 → 现在先收图再判断，纯图消息也能接 |
| 私聊拍一拍判不出来 | 判定写的是 `message['pat_target_id']`，而接口给的是 `message['pat']['target_id']`（字段根本不存在，判断永远为假）→ 改用 `pat.target_id` 和自己的 user id 比 |
| 演习模式偷偷改了线上状态 | 新加的 `mark_channel_read` 没走 `DRY_RUN` 判断，演习时照样 POST 了已读 → 凡是“写”操作，一律先看 `DRY_RUN` |
| 带图时 `response_format=json_object` 报 400 | DeepSeek 要求提示词里出现 `json` 字样，跟图无关 → 提示词里保留 `EXAMPLE JSON OUTPUT` |
| 时间戳凭空多 8 小时 | 站点时间戳是“UTC+8 墙上时间贴 Z 标签”；本项目不解析时间，故无影响 |

## 状态文件

`neko_state.json`（演习模式写 `neko_state.dryrun.json`，两者都不入库）：

| 字段 | 含义 |
| --- | --- |
| `last_comment_id` | 评论轮询锚点（UUID，只能记“最新那条”） |
| `last_chat_id` | 聊天区轮询游标（消息 id 自增） |
| `dm_cursors` / `dm_primed` | 每个私聊会话各自的游标；`dm_primed` 表示“开局水印已记好” |
| `handled_comments` / `handled_chat` | 已回复过的触发 id（去重表，最多留 1000 条） |
| `comment_reply_times` / `chat_reply_times` / `dm_reply_times` | 三条通道各自的回复时刻，用于小时限额 |
| `last_chat_reply_at` | 上次在聊天区说话的时刻，用于最小间隔 |

删掉它 = 让她忘掉一切；但**首次运行不会回补历史**（避免上线瞬间刷屏）。
想先看历史会怎么回，用 `NEKO_DRY_RUN=1 NEKO_REPLAY_BACKLOG=1`。

## 已知限制

- 私聊只**被动回**：不会主动开新会话（接口支持，未实现）；群里 @ 她才有通知，私聊没有“未读提醒”可依赖，全靠轮询；
- 用轮询而不是 SSE：评论本来就没有推送；聊天有 SSE，但轮询更简单、够用；
- 图片能看，但**不是万能的**：私有图 / 已删的图 / SVG / 超 8 MB 的图一律当没有；
  动图只抽 4 帧，细节靠抽样；一条消息最多 3 张；
- 拍一拍、纯表情、图已失效的“空消息”仍然不回复（没有任何可判的内容）；
- 长文摘要会丢细节——她“读”到的只是摘要加上你自己那句话；
- 内置哈希向量擅长找到用词相近的中文内容，但对同义转述的理解弱于真正的 embedding 模型；需要时可通过 `NEKO_EMBEDDING_*` 切换；
- 状态是单机文件：换台机器或删掉文件就等于失忆，别指望多机部署。
